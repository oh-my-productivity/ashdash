# Performance (Wave 4 re-measure)

Measured for the v0.1.0 release candidate on 2026-10-16, branch `wp/w4-rel` (base `main`, Waves 0-3), release profile (`cargo bench` = optimized).
Nothing in the product was tuned for these numbers.

## Machine and conditions

* Apple M3 Pro, 12 cores, 36 GB RAM, macOS 26.5.2, rustc 1.95.0.
* **The machine was not idle.** It is the user's working desktop: a Tart VM was running, another worker (W4-FIX) was building/testing in a different worktree, WindowServer and iTerm were busy.
  `uptime` load averages (1/5/15 min) around the runs: 4.7/5.8/5.8 (run 1), 7.0/6.2/5.9 (run 2), 6.3/6.1/5.9 (run 3), 4.8/5.7/5.8 before the criterion run and 6.0/6.3/6.0 after it.
  Summed `%CPU` of all other processes at the start of the three runs: 126 %, 229 %, 190 % (of 1,200 %). 12 cores means the benches (single-threaded query loops) still had a free core,
  but treat every number as "measured on a busy laptop"; the spread across the three runs is given so you can judge it.
* Synthetic data only: fake `.app` bundles with a minimal `Info.plist` generated by `ashdash_core::index::synth` / the report bench, synthetic clipboard text, a synthetic file tree in `$TMPDIR`.
  No user data was read. The "real scan" line counts apps in `/Applications` only.

## Commands

```sh
# human-readable report: apps at 500 and 5,000, clipboard history, file-search walk budget, real app folders
cargo bench -p ashdash-core --bench report            # run 3 times
ASHDASH_BENCH_APPS=5000 cargo bench -p ashdash-core --bench report   # app counts are overridable (comma list)
# criterion: query latency, cold start and fuzzy scoring at 5,000 apps (about 2.5 minutes)
cargo bench -p ashdash-core --bench queries
```

`report.rs` was extended in this wave (it is under `crates/core/benches/`): it now runs the app section for 500 and 5,000 apps, and has new clipboard-search and file-budget sections.
Per-query numbers come from 300 timed calls after 20 warm-up calls per query string; queries are `saf`, `vsc`, `visual studio`, `x`.

The two warm-start figures differ about 5x (`report`: 5.5-8 ms median to first query; criterion `Engine::new` + first query: 36 ms). Both build an `Engine` over the same warm cache and run one query, but
the criterion loop runs back-to-back engine constructions with their watcher/refresh threads from the previous iteration still winding down. The difference was not investigated; both are far below the target and the
real first launch is the "no cache" row.

### Clipboard history search (`ClipboardHistory::search`, 20 results, in memory; JSON load is not included)

| Entries | `saf` p95 | `visual studio` p95 | no match p95 | spread of `visual studio` p95 over 3 runs |
|---|---|---|---|---|
| 200 (default cap) | 0.25-0.29 ms | 0.27-0.29 ms | 0.27-0.28 ms | 0.274-0.287 ms |
| 1,000 | 1.19-1.24 ms | 1.36-1.42 ms | 1.36-1.38 ms | 1.364-1.419 ms |

Cost is linear in entry count (about 1.4 µs per entry: fuzzy score of the label plus a lowercase `contains` over the text). At the shipped default of 200 entries it is far inside budget; at
5,000 entries it approaches the 10 ms line (see "Findings").

Synthetic tree of 10,000 files in 440 folders. Searching for a name that exists once:

| Budget | Result | Wall time (median over 5, spread over runs) |
|---|---|---|
| default (200,000 entries, 2 s) | 1 hit, `Complete` | 14.4-21.0 ms |
| `walk_max_entries = 1,000` | 0 hits, `Partial` | 1.4-1.6 ms |
| `walk_timeout = 5 ms` | 0 hits, `Partial` | 5.2-5.7 ms (stops at the limit plus about 0.2-0.7 ms) |

### Real application folders

`apps::scan` of `/Applications`, `/System/Applications`, `~/Applications`: 81 apps in 12.5-22.8 ms (run 1: 22.8, run 2: 18.2, run 3: 12.5 ms; warm file cache).

## Findings and honest caveats

* No target that could be measured without the GUI was missed.
* `ashdash` has no headless daemon mode: running the binary with no arguments starts the launcher window, which needs the desktop. So the idle RSS/CPU of the real process, the time to
  hotkey-ready and the time to show the window are all open. Suggested manual check (on a VM from WP14 or with the desktop mutex): `ashdash &` , wait 10 s, then
  `ps -o rss=,cputime= -p $(pgrep -x ashdash)` twice 60 s apart.
* 47 MB at 5,000 apps is the bench process (it also holds the synthetic name list and the benchmark's allocations), so it is an upper bound for the engine alone, but egui/eframe plus a
  hidden window typically add tens of MB on top. The 80 MB target is plausible at ~80 apps (a real Mac; engine about 15 MB) and uncertain at 5,000 apps. Measure before claiming it.
* The no-cache start (225-252 ms at 5,000 apps) happens once per cache loss and runs on the construction path. It is inside the 300 ms target alone but would exceed it with any additional start-up work.
* Clipboard search is O(entries); with the retention cap raised to several thousand entries one search costs 6-7 ms of the 10 ms budget. The default cap (200) is fine. Candidate for later: pre-lowercased labels
  as the app index does. Not changed (no tuning in this task).
* Variance: run-to-run spread is below 10 % for all steady-state numbers and larger (up to 2x) for sub-millisecond start-up numbers, which is within the noise of a busy machine.
  The load was not "quiet" as the brief asked; the figures are indicative, and a re-run on an idle machine can only improve them.
